## 一、核心功能管理

### 1.1 工作台（Dashboard）`/console`

**当前状态**：调用 `GET /api/admin/dashboard/overview`，后端已有此端点。统计卡片、趋势图、热门问答、待办事项均可返回真实数据。

**缺陷按钮**：
- 「导出报表」— 无 onClick
- 「刷新数据」— 无 onClick
- 待办事项的「处理」按钮 — 无 onClick

**优化方案**：

| 数据项 | 来源 |
|--------|------|
| 今日服务人次 / 累计问答 / 满意度 | 后端实时统计（已有） |
| 景点总数 | `scenic_spots` 表 count（已有） |
| 知识文档 | `knowledge_documents` 表 count（已有） |
| 趋势图 | 7 天 ChatRecord 聚合（已有） |
| 热门问答 Top5 | ChatRecord GROUP BY（已有） |
| 待办事项 | 草稿文档数 + 待处理反馈数（已有） |

**行动**：
1. 导出报表 → 改为触发后端生成 CSV/Excel 下载
2. 刷新数据 → 重新调用 `getDashboard()`
3. 处理按钮 → 点击跳转到对应管理页（文档→知识库，反馈→满意度）

### 1.6 景点讲解管理 `/console/spots`

**当前状态**：❌ 100% 静态 mock。数据来自 `admin-data.ts` 的 `narrationSpots`、`narrationSamples` 等。

**优化方案**：

**保留静态数据的部分**：
- 讲解风格预设（知性讲解/生动故事/简洁导览/禅意讲述）— 配置类数据，可保留在前端常量
- 篇幅档位（简短/标准/详尽）— 同上

**需要接入真实数据的部分**：

| 数据项 | 来源 |
|--------|------|
| 景点列表（名称、分类、启用状态） | `GET /api/admin/spots/admin-list`（后端已有） |
| 今日生成讲解次数 | ChatRecord 中 intent="guide" 的 count |
| 平均生成耗时 | ChatRecord 中 response_time_ms 的 avg |
| 讲解满意度 | ChatRecord 中 satisfaction_score 的 avg |
| 近期讲解样本（质量审核用） | ChatRecord 按 created_at 倒序取前 10 条 |

**行动**：
1. 调用已有的 `getAdminSpots()` 加载景点列表
2. 启用/禁用开关 → `PATCH /api/admin/spots/:id/toggle`
3. 新增后端 `GET /api/admin/spots/stats` 返回讲解统计
4. 讲解样本从 ChatRecord 表抽取
5. 「预览生成」→ 触发后端用当前配置生成一段示例讲解

### 2.2 游客行为分析 `/console/behavior`

**当前状态**：❌ 100% 静态 mock。图表数据如漏斗、时段分布、渠道占比全是假数据。

**优化方案**：

**保留静态数据（合理且展示效果好）**：
- 行为漏斗（进入→浏览→收听→路线→明信片）— 典型转化路径，可用静态比例
- 设备分布（iOS/Android/大屏）— 无法真实获取，保留 mock
- 渠道分布（扫码/小程序/终端）— 同上

**可接入真实数据的部分**：

| 数据项 | 来源 |
|--------|------|
| 今日活跃游客 | `users` 表当日 last_login count |
| 人均停留时长 | 从 ChatRecord 时间跨度估算 |
| 讲解收听次数 | ChatRecord intent="guide" count |
| 时段流量分布 | ChatRecord 按 hour(created_at) 聚合 |

**行动**：
1. 新增后端 `GET /api/admin/behavior/stats` — 返回可统计的指标
2. 漏斗/渠道/设备保留静态 mock
3. 「导出」按钮 → 触发后端生成 CSV

---

### 2.3 数据大屏 `/console/screen`

**当前状态**：❌ 纯前端模拟。KPI 数值用 `setInterval` 随机递增，完全不连后端。

**优化方案**：

| 数据项 | 来源 |
|--------|------|
| KPI 卡片（入园人数、导览调用、讲解播放等） | `GET /api/admin/screen/summary`（后端已有端点，页面未调用） |
| 游客趋势（近 7 天） | `GET /api/admin/screen/trend`（后端已有） |
| 地域分布 | `GET /api/admin/screen/region`（后端已有） |
| 功能使用占比 | 从 ChatRecord intent 分布统计 |
| 年龄/性别分布 | `GET /api/auth/tourist-stats`（**后端已有，已完成**） |
| 实时事件流 | ChatRecord 最新 10 条（轮询即可，不必 WebSocket） |

**行动**：
1. 页面加载时调用 `getScreenSummary()`、`getScreenTrend()`、`getScreenRegion()`
2. 年龄/性别从 `getTouristStats()` 获取
3. 保留 `setInterval` 但改为每 30 秒重新拉取 API（而非随机数递增）
4. 实时事件从 ChatRecord 最新记录生成

**混合方案**：保留 mock 中的用户作为展示数据，同时接入真实用户数据。

2. 新增后端 `GET /api/admin/users/stats` — 统计

**当前状态**：❌ 100% 静态 mock。

**优化方案**：

**保留静态数据**：角色权限是典型的配置型数据，6 个角色（超级管理员/内容运营/数据分析师/客服专员/讲解编辑/访客只读）和 9 个权限模块均为固定设计，无需动态 CRUD。

> **建议**：保留静态为主，比赛评委更关心功能设计而非真实权限系统。

### 3.3 系统设置 `/console/settings`

**当前状态**：❌ 100% 静态，表单提交只弹 toast。

**优化方案**：

**保留静态数据**：系统设置本质是配置表单。可以保留默认值 + localStorage 持久化。

**行动**：
1. 保存时写入 localStorage，加载时从 localStorage 读取
2. 「恢复默认」重置为硬编码默认值
3. 「清除缓存」→ `localStorage.clear()` + 刷新
4. 如果后续需要多管理员共享配置，再建 `system_config` 表

> **建议**：用 localStorage 实现即可，比赛中能演示"保存→刷新→仍在"即可。

### 3.4 日志管理 `/console/logs`

**当前状态**：❌ 100% 静态 mock，10 条假日志。

**优化方案**：

**新增后端操作日志表**：

| 字段 | 说明 |
|------|------|
| id | 主键 |
| user | 操作人 |
| type | 登录/操作/系统 |
| level | 信息/警告/错误 |

**行动**：

2. 后端 CRUD：`GET /api/admin/logs/list`（分页+筛选）、`DELETE /api/admin/logs/clean`
3. 在关键操作（创建文档、删除文档、用户注册等）处插入日志记录
4. 前端接入 API，保留 mock 中的 10 条作为种子数据
